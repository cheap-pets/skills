# 代码注释规范

读者是半年后没有当前上下文的人或 agent。先改进代码（命名、提取函数、类型、断言），不用注释复述实现或掩盖设计问题。项目 AGENTS.md 或用户对注释的明确要求优先于本规范。

## 两条主规则

1. **取舍**：删掉这条注释，不熟悉代码的读者会做错事，或要花明显代价推断吗？不会就不写。需跨文件追踪才能确认的关键行为算明显代价，但必须是本次已确认的；只读函数体就能看懂的不算。
2. **依据**：注释中的原因必须有需求、代码、文档或用户说明作依据。不确定就不写，不编造。

## 通过取舍的典型情形

- 原因与约束：业务规则、外部限制、兼容原因、不明显的方案取舍
- 隐含行为：边界条件、调用顺序、副作用、并发 / 时序要求、外部约定
- 保护性说明：看似多余但不能删改的代码，及改动后果

## 不写

- 复述代码、名称、签名、类型
- 变更叙述、过程汇报、对话痕迹（属于 commit / PR / 对话）
- 注释掉的代码、无后续动作的 TODO、横幅
- 行号、调用方清单、临时状态等易过期信息

## 写法

- 默认 1 行，必要时不超过 3 行；超出先精简措辞，不丢必要信息。
- 结论先行，一条一事；用具体值、单位、条件，不用“可能、适当”等模糊词。
- 语言和格式跟随所在文件与项目；无参照时用对话语言。标识符原样引用，紧邻所说明的代码。
- **API 文档**：面向调用者，按项目要求编写；只补充签名无法表达、且正确使用接口所必需的信息，不机械复述，不强制每个成员都写。
- **TODO / FIXME**：写明待办事项和触发条件，有 issue 编号则附上。
- **lint / 类型检查抑制**：写明具体原因，范围最小；优先解决根因。

## 维护与评审

- 改代码时检查受影响的注释和文档：过期则更新，失去价值则删除；不批量清理无关代码。过期注释会被后续 agent 当作事实，视同缺陷。
- 评审时只指出错误、过期、无依据或误导的注释，以及缺失的关键说明；不对风格挑刺。
