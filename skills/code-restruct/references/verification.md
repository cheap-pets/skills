# 验证方法、告警口径与探针基线程序

配套 `SKILL.md` §5 验证矩阵与步骤 3、4。各语言具体执行命令见 `references/lang-<stack>.md` §4。

> **按需读取原则**：常规重构直接按 `SKILL.md` §5 的默认验证组合（编译/类型检查 + 既有测试 + 残留引用扫描 + `git diff` 核对）执行；仅当命中 R4 触点且无自动化测试覆盖、或 T2b/T3 目标路径无自动化测试覆盖时，才按本文件执行探针基线或降级程序。

## 1. 告警基线与测试覆盖判定口径（全语言通用）

### 1.1 告警基线口径
历史代码库在重构起点往往已存在编译或 Linter warnings。若直接附加 `-warnaserror`、`-D warnings` 或要求 `ruff check` 零告警，会导致验证在起点即失败。

- **标准做法**：在步骤 3 批前检查时，记录起点 HEAD 的 build / 类型检查 / Linter 告警数量或输出摘要；改码后同命令复测，**以“零错误且不新增告警”为通过标准**。
- **严格零告警门禁**：仅当起点 HEAD 本身已实现零告警时，才启用 `-warnaserror`（C#）、`-- -D warnings`（Rust）或零 warning 退出码门禁。

### 1.2 “无自动化测试覆盖”判定口径
- 在项目测试目录（如 `tests/`、`test/`、`__tests__/`、`*.spec.*`、`*.test.*`）及内联测试块（如 Rust `mod tests`）中 `grep` 本批目标文件名或导出的函数/类/组件符号：
  - **未发现任何 `import` / `use` 或直接调用** → 判定为**无自动化测试覆盖**。
  - **无法确认是否触达目标分支** → 保守按**无自动化测试覆盖**处理。

## 2. 核心验证方法与失效边界

| 方法 | 验证什么 | 失效边界与对策 | 成本 |
| :--- | :--- | :--- | :--- |
| **build / 类型检查** | 语法、模块导入解析与静态类型契约 | **不覆盖运行时字符串契约**（模板属性名、emit 事件名、JSON 序列化键、反射/动态属性访问、i18n 键）。Vue 项目必须运行 `vue-tsc --noEmit`（仅跑 `tsc` 无法检查 `<template>` 绑定） | 低 |
| **既有测试（只读冻结）** | 已有自动化用例的原样通过状态 | **重构期间严禁修改测试断言**；若必须改测试断言才能过检，说明行为已变，立即按 R4 回滚本批 | 低 |
| **残留引用扫描** | 旧符号、旧路径引用清零 | `git grep` 默认不含未跟踪（untracked）的新建文件；应使用 `grep -rnw` 或 `git grep --untracked` 扫描全仓 | 低 |
| **`git diff --color-moved` 核对** | T2a 纯搬移内容零篡改、T1/T4 引用与参数位逐一配对 | 搬移块内若夹杂表达式微调会被高亮区分，核对时确保除导入/导出修饰符外，函数体逻辑逐行全等 | 低 |
| **API 冻结核对** | 包对外公共入口的导出符号、公共类型签名、事件契约零变化 | 用 `git diff` 检查公共入口文件与导出签名，确保外部消费方无感知 | 低 |
| **状态与生命周期顺序核对** | T2b 抽离 Composable / 子服务后，状态初始化与钩子注册时序不变 | 人工或 AST 核对 `watch` / `onMounted` / 构造函数注入 / `Drop` 析构的相对先后顺序 | 中 |
| **人工冒烟清单（T2b 替代项）** | 无自动化测试的 UI/交互组件在 T2b 拆分后的核心行为 | 经用户确认后，由 Agent 生成本批触达页面的 3–5 项最简交互检查点交用户快速点验，替代高成本探针基线 | 低 |
| **单次探针基线比对** | 无测试覆盖且命中高危触点时的运行时可观测输出等价 | 仅覆盖探针触达的执行路径；采集与比对程序见 §3 | 高 |

## 3. 单次探针基线程序（仅触发例外条件时启用）

当改动命中 `SKILL.md` §5 右列的探针基线触发条件，且用户未选择人工冒烟替代时，执行以下简化程序（**取消原版“每批默认连采两次”的冗余要求**）：

1. **采集口径**：
   - **前端**：控制台 `console.warn` / `console.error` 原文序列 + 关键渲染节点计数或 DOM/组件快照。
   - **后端 / 通用栈**：测试或脚本标准输出、接口响应 JSON 载荷、结构化日志序列。
2. **改前单次采集**：
   - 在本批改码前采集 **1 次**，落盘至 `docs/restruct/<模块>/baseline/<批>/`（或临时基线目录），记录当前起点 HEAD 的 commit hash。
3. **改后复采与比对**：
   - 改码完成后，以完全相同的口径复采 **1 次**，剔除已知非语义漂移（时间戳、随机 ID、内存地址、行号）后执行 `diff`。
   - **diff 为空** → 验证通过。
   - **diff 非空** → 先排查是否为代码改动引入的行为变化；若怀疑是原代码固有的非确定性输出，再切回原起点 HEAD 补采 1 次验证。确属行为变化的，按 R4 立即回滚本批。

## 4. 无运行/无测试环境时的降级路径

当目标模块既无自动化测试，又无法在当前环境启动运行时探针时，按以下顺序降级：

1. **优先执行免探针基线改动**：正常推进所有 **T1（无触点）**、**T2a（纯函数/常量/类型外提，静态排除顶层副作用）** 与 **强类型 T4（无当值传递）** 批次——这三类靠静态类型检查、`git diff --color-moved` 与残留扫描即可闭环，无需运行环境。
2. **补充轻量特征测试（独立先行提交）**：若核心痛点必须通过 T2b / T3 解决且具备单测运行器，先针对目标函数写最小特征测试并单独 commit，再启动重构批。
3. **生成人工冒烟清单或推迟**：若连单测运行器也无法执行，将 T2b / T3 批推迟并记入不做清单（理由：当批风险不可控），或输出明确的人工验证步骤交由用户在本地环境确认。**严禁在无类型、无测试、无验证的情况下盲目合入 T2b / T3 改动。**
