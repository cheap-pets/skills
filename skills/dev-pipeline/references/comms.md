# 沟通、上限守门、未解问题与结束汇报（停点 / 异常 / 结束时读）

## 1. 必须停下询问用户的情形（任何开关下均不可跳过）

- 任一循环上限耗尽（设计修订 `k >= N` 进检查点；修复轮 `k >= R`、回设计 `j >= 回头上限`、回方案 `j >= 回头上限` 停下给三项选择）。
- 验收标准需要修改或削减。
- 涉及破坏性操作（删除业务数据、修改生产配置、安装或升级依赖、`implementer` 返回 `BLOCKED(需确认)`）。
- 人工意见被 `designer` 标为“不可行”。
- 需要第 2 次补探索（`01-explore-补-1.md` 已存在）。
- 任意角色返回 `决策冲突 > 0`（与 `decisions.md` 冲突）。
- `pipeline-ctl.mjs verify-readonly` 检出只读/受限角色发生越权文件修改，或 `check-scope` 检出未获豁免的 `清单外改动`。
- 验证报告存在「环境阻塞」。

**上限耗尽的三项选择（统一措辞）**：
1. `追加 <数>`：将对应上限（`N` / `R` / `回头上限`）上调，更新 `00-task.md` 并记入 `decisions.md` 后继续循环；
2. `接受当前结果`：将已知遗留问题记入 `decisions.md`，跳过剩余循环进入下一阶段或结束汇报；
3. `终止`：停止流水线，保留全部已有产物，按下方「结束汇报」模板输出。

## 2. 未解问题处理（通用规则）

当任意角色返回 `未解问题 > 0` 时，调度者读取该产物的「未解问题」节：
- **属需求 / 业务裁决类**：合并为一次提问交用户回答，用户答复记入 `decisions.md`；
- **属代码事实待查类**：若 `01-explore-补-1.md` 尚不存在，自动派 `explorer`（`executor`）输出 `01-explore-补-1.md`（若已存在则先询问用户是否允许第 2 次补探索）；
- **消化更新**：拿到用户答复或补探索报告后，若当前处于设计阶段，派 `designer / 修订` 直接更新 `02-design.md` 受影响部分（不写回应文件，不计入自动修订额度 $k$），随后进入原定下一阶段。

## 3. 人工修订（设计检查点）

用户在设计检查点发出“修订：<意见>”或独立提出设计修改意见时：
1. 调度者将用户意见**原文**按 `- [K-n] <用户原文>` 写入 `03-human-K.md`（首行 `VERDICT: REVISE`；每条默认按 blocker 处理，用户另有说明除外），要点记入 `decisions.md`。
2. 派发 `designer / 修订`（读取 `02-design.md` 与 `03-human-K.md`，更新 `02-design.md` 并输出回应文件 `02-response-人工-K.md`；人工修订不计入自动修订额度 $k$）。人工意见严禁标“不接受”；若确属不可行，标“不可行”并附代码证据，调度者立即停下交用户裁决。
3. 修订完成后，默认派 `design-reviewer` 重审（输出 `03-review-(r+1).md`），重审后直接回到检查点（即使返回 `REVISE` 也不再触发自动修订循环）；若用户明确说明“修订后不用再评审”，则跳过重审直接回检查点，设计状态标 `未经评审`。
4. **微改动快速路径**（窄例外，替代步骤 2–3）：内容已由用户逐字确认且 ≤ 数行时（拿不准即按常规流程），可跳过 `designer` 更新 `02-design.md` 与 `design-reviewer` 重审：先将「微改动快速路径」豁免与理由记入 `decisions.md`，再以 `03-human-K.md` 为改动依据直接派 `implementer`（输入追加 `03-human-K.md`，追加约束注明`一并自查`）修改 + 自查；该项 `check-scope` 按预期清单外处理（见 `pipelines/impl-verify.md` 路由细则 2）。

## 4. 流水线期间的修改请求路由

自任务目录建立起至结束汇报前，若用户在非检查点主动提出修改请求：
- **先区分提问与祈使指令**：若用户使用疑问句或探讨性语气（如“这里能不能改成 X？”“为什么不用 Y？”），**先直接回答问题，不触发子智能体派发**；仅当用户发出明确祈使修改指令且未指定由谁执行时，按以下路由派发并一行告知：
  - **改设计** → 按上方「人工修订」写 `03-human-K.md` 并派 `designer / 修订`；
  - **改源码** → 将用户意见原文按 `- [K-n] <用户原文>` 写入 `05-human-K.md`（首行 `VERDICT: FAIL`），派 `implementer / 修复`（**输出命名为 `04-impl-<键>-人工修复-K.md`**，与自动修复文件区分，不计入自动修复轮 $R$；若此前 `implementer` 产物处于 `进行中` 未定稿，先完成接续再执行本次人工修复）；
  - **补查代码事实** → 派 `explorer`；
  - **重新验证** → 先跑 `check-scope`，再派 `verifier`。
- **调度者可直接处理的窄例外**（拿不准即派发）：
  1. 用户明确要求调度者本人直接修改；
  2. 仅涉及调度者职责文件（`00-task.md` / `00-repro.txt` / `decisions.md` / `run.log` / 人工意见文件）；
  3. 单文件纯文案、注释或格式微调，完全不影响运行行为且不触碰测试与配置（做后一行告知并记入 `decisions.md`）；
  4. 与当前任务完全无关的请求 → 提示用户另开会话处理；
  5. 要求安装依赖或修改构建环境 → 按第 1 节「必须停下询问用户」处理（子智能体严禁安装依赖）。

## 5. 结束汇报模板

流水线完成或终止时，汇报总长度控制在 **≤20 行**（改动文件摘要不占行预算），无内容的项整项省略；设计类流水线仅输出第 1、2、6 项：

1. **产物目录与模型配置**：`.pipeline/<yyyymmdd>-<slug>/`；标注 `评审模型：异构 | 同模型独立 | 宿主默认`；
   - **改动文件摘要**（实施类必填）：相对 `00-baseline.txt` 发生改动的源码文件（≤3 行，超出按目录归并，完整清单指向 `git diff --stat <基线HEAD>`）；附一行还原提示：`未提交改动可由用户执行 git checkout -- <文件> 还原（调度者不代做）`。非 git 仓库改为列出改动文件清单并提示按清单手动还原（无 `git checkout` 可用）。
2. **核心结论**：各阶段关键 verdict；设计最终状态（`通过` / `未通过` / `未经评审`）；循环计数汇总（`设计修订 k/N；回设计或回方案 j/上限；各键修复轮 k/R`）。
3. **未验证与豁免项**：`UNVERIFIED` 条目、需人工检查步骤、环境豁免或清单外改动豁免说明。
4. **验收入口**（≤3 行摘要 + 指向终验 `PASS` 报告「验收入口」节路径；无则写 `无：<原因>`）。
5. **合并风险与建议人工定点审阅**：
   - 合并风险（1 行，取自 `02-design.md`「风险与回滚」）；
   - 建议人工定点审阅（≤3 条 `path:line` + 原因；仅在单向门风险、清单外豁免、或修复耗尽强行接受时输出）。
6. **遗留问题与自动化加固建议**：
   - 遗留未解问题或规范审查遗留 minor（≤5 条标题 + 报告路径）；
   - 若本次任务发生过 `回设计 / 回方案 >= 1`、任一键 `修复轮 >= 2`、或规范审查同类问题 `>= 2` 条，附 **1 条“让机器自动拦住”的工程固化建议**（如新增 lint 规则、架构单测或 `AGENTS.md` 约束）。
