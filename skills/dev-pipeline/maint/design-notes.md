# 核心架构取舍与设计理由备忘录（维护文档，不进入运行时加载图）

本备忘录保存从各运行时协议文件中剥离出的“为什么这样设计”的背景与工程权衡，保持运行时文件纯粹为祈使句执行规则。

## 1. 为什么删除成本记账子系统（`d` / 预估 / 1.5 倍软提示 / `metrics.md`）
- 原协议中的“预估派发次数”是将所有循环上限（$N, R, j$）按最坏情况满打代入算出的最大值，而软提示阈值设为预估的 1.5 倍，导致正常自动循环永远不可能触发软提示（只有靠大量人工插话修订和限流重派才能凑够批次）。
- 批次序号 `d` 在规则上“任何情形下不触发停线”，真正起刹车作用的只有 $N$、$R$、$j$ 三个控制上限。
- 墙钟耗时、Token 消耗量、调度者自身失误数由 LLM 在运行时自采极不准确，移交会话日志外部统计后，可减去约 18% 的运行时协议噪音。

## 2. 为什么去掉共享工作区并发实施，且连带删除“集成片”与“片级白名单”
- 验证阶段（lint / typecheck / test / build）由于共享工作区、端口与构建缓存，本就只能串行执行；并发实施仅缩短编码阶段的墙钟时间，却不节省任何 Token。
- 为了在同一个 Git 工作区里防并发写冲突，原协议引入了“片级文件白名单”、“整批返回后才做 `git status` 归因”、“跨片失败标`他片相关`”、“他片半成品崩溃豁免”以及“把路由/导出/i18n 剥离到末尾的串行集成片”。
- 更严重的是，在串行逐片模式下，把路由注册和公共导出剥离到“集成片”会导致前面的业务片在片验证时根本无法端到端触发，直接违背了“每片是端到端可验证的最小纵向行为”的设计原则。因此砍掉共享工作区并发实施、集成片与片白名单（真需并发时用 `git worktree` 物理隔离）可一次性消除 6 处跨文件复杂规则。

## 3. 为什么采用“文件名 + `r_base` 锚点”推导计数，而不采用 YAML Frontmatter 或单文件 `04-impl` 快照
- 若把 `04-impl` 改为单文件覆盖快照，就会丢失历史修复轮次的文件个数，迫使计数重新依赖文件内部的 YAML 可变字段，且破坏了追加式审计轨迹。
- 保留 `04-impl-<键>-修复-N.md`（自动修复与逐片停点修复）并将会话中途的人工修复命名为 `04-impl-<键>-人工修复-K.md`，即可直接通过文件个数 100% 确定性推导每键修复轮 $k/R$。
- 在“回设计”场景下，若取消设计修订计数 $k$ 的清零，当首次设计已用满 $N=2$ 轮修订时，一旦 P4 实施触发回设计，回设计后的首次评审只要返回 `REVISE` 就会立即触发耗尽停线，使回设计失去自动打磨新方案的能力。因此在 `decisions.md` 的回设计标记中记录 `[回设计 j | r_base=<当前最大评审序号>]`，由 `pipeline-ctl.mjs status` 统计 `r > r_base` 的 `02-response-<r>.md` 个数，既实现了无状态文件推导，又保留了回设计后完整的修订周期额度。

## 4. 为什么删除 `design-reviewer` 的交叉改稿模式與 `bugfix-verify` 的无设计直修模式
- **交叉改稿模式**：原规则要求评审员直接 Edit `02-design.md` 并手抄一份 Markdown 改动台账，且只要有实质改动仍须返回 `REVISE` 交设计者复核（设计者不接受还要手动 Edit 回滚文本）再交评审员复审。这不仅一轮往返都没省下，还打破了 `02-design.md` 的单写者原则（Single-Writer Principle），且 `.pipeline/` 通常被 gitignore，用户也无法直接用 `git diff` 审阅。
- **无设计直修模式**：仅比 `B2（designer / 缺陷修复模式，≤3 步薄设计）` 少 1 次派发，却迫使 `explorer` 违背“只给事实不给方案”的边界去写修复方案，并迫使 `implementer`、`verifier`、`code-reviewer` 三个底层契约到处打满“无设计文档时……”的条件补丁。统一走 `B1 -> B2 -> I1 -> I2` 后，所有实施阶段均有结构统一的 `02-design.md`。

## 5. 为什么 `verify-readonly` 必须采用派发前 `save` 与返回后 `check` 的快照对比
- `00-baseline.txt` 记录的是整个任务启动时的源码基线。当流程推进到 P2 多轮修订或 P4 验证阶段时，`02-design.md` 与业务源码早已发生了合法修改。
- 如果在 `design-reviewer`、`verifier` 或 `code-reviewer` 返回后只拿 `00-baseline.txt` 比对，就会把前序 `designer` 或 `implementer` 的合法修改误判为当前只读角色的越权写入。因此由调度者在派发只读/受限角色前执行 `verify-readonly <task_dir> save` 拍下即时快照，返回后执行 `verify-readonly <task_dir> check --allow <允许路径...>`，即可精确锁定本次派发期间的文件变动。
